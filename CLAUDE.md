## Cos'è questo progetto

Nomad-Net è un prototipo software di rete distribuita, **content-centric** e **delay-tolerant**: dispositivi condividono contenuti, servizi e messaggi senza infrastruttura Internet, tramite mesh locali, store-and-forward, caching opportunistico e sincronizzazione automatica al ritorno della connettività. Ispirato concettualmente a BitChat (mesh BLE) e pensato per integrarsi con Project NOMAD come "service provider" locale (Kiwix, Ollama, ecc.), ma senza dipendere da nessuno dei due.

**Specifica completa e single source of truth**: [`docs/SPECIFICATION.md`](docs/SPECIFICATION.md) (in italiano, numerata per paragrafi §N — tutti i riferimenti nel codice e nei commenti usano questa numerazione). Se qualcosa nel codice sembra contraddire questo file, la specifica vince; se manca un dettaglio, cercalo lì prima di indovinare.

**Repository GitHub**: `ciao-madesign/nomad-net`. **Branch di lavoro**: `claude/nomad-net-project-spec-lcnbqt`.

## Workflow da riusare per lavoro futuro (voce, feature, o passata di qualità)

Il workflow concordato con l'utente, usato per ognuna delle 10 voci sopra e da riapplicare identico a qualunque lavoro sostanziale futuro in questo repository:

1. Implementa la feature.
2. Scrivi/aggiorna i test (unit + integration, seguendo le convenzioni esistenti — vedi sotto).
3. Fai girare l'intera suite più volte di fila (`npx vitest run`, ripetuto 3-15x a seconda della sensibilità a timing/race) per scovare flakiness prima che la trovi la revisione.
4. Invoca la skill `code-review` con un prompt dettagliato che spiega cosa è cambiato e dove concentrare l'attenzione — non un generico "rivedi questo diff".
5. Correggi i problemi reali trovati (non solo quelli comodi), aggiungi test di regressione dedicati per ciascuno, ri-verifica.
6. Aggiorna `docs/security.md` (nuova voce numerata) e `docs/protocol.md`/altri doc pertinenti.
7. `npx tsc --noEmit -p node/tsconfig.json` e `npm run build -w node` puliti.
8. Commit con messaggio dettagliato (cosa, perché, cosa ha trovato la revisione), push su **sia** `claude/nomad-net-project-spec-lcnbqt` **sia** `main`.
9. Report all'utente in italiano, **poi fermati e aspetta un "ok" esplicito prima di iniziare il prossimo pezzo di lavoro** — istruzione esplicita data dall'utente all'inizio dell'arco di 9 voci ("Dopo ogni step aggiornami e chiedimi ok per proseguire"), non legata alla singola serie di voci ormai conclusa: vale per qualunque lavoro sostanziale futuro allo stesso modo.

Non saltare il passaggio di code-review nemmeno quando il codice "sembra ovviamente corretto": in ogni voce fatta finora ha trovato almeno un problema reale (spesso più di uno) prima di considerare la voce conclusa — inclusi almeno due crash-DoS reali (accesso non protetto a un campo di payload potenzialmente assente) e diverse race condition/edge case di conteggio.

### File chiave in `node/src/` e a cosa servono

- `identity.ts` — identità Ed25519 per nodo (`Identity`), firma/verifica.
- `packet.ts` — `MessageType` enum, formato pacchetto, `Priority` enum (spec §50), encode/decode newline-JSON.
- `transport.ts` — interfaccia `Transport` astratta; `transports/tcp.ts` è l'unica implementazione reale finora; `transports/ble.ts` (voce #8) e `transports/lora.ts` (voce #51, Opzione N) ne sono due simulate, zero radio reale, dietro la stessa interfaccia — entrambe thin wrapper su `transports/simulated-link.ts` (vedi sotto), affiancabili sullo stesso `NomadNode` via `addTransport()`. `transports/beacon-broadcast.ts` (voce #56, vedi sotto) è deliberatamente **fuori** da questa interfaccia — un dispositivo che non accetta mai connessioni non ha senso forzato in `connect()`/`onPeerConnected()`.
- `transports/simulated-link.ts` (voce #51, esteso in voce #56) — `SimulatedMedium` (registro condiviso in-process "prossimità fisica", device id → transport) e `SimulatedLinkTransport implements Transport` (connessione punto-a-punto simulata, handshake HELLO, frammentazione/riassemblaggio a MTU via `FragmentReassembler`, limite di connessioni con reconnect-displacement) — estratto da `ble.ts` quando `lora.ts` ha avuto bisogno esattamente della stessa meccanica, configurato interamente via un oggetto di opzioni risolto (`id`/`radioLabel`/`mtu`/`maxConnections`/`latencyMs`/`medium`), nessun default radio-specifico in questo file. `BleMedium`/`LoraMedium` (in `ble.ts`/`lora.ts`) sono sottoclassi di `SimulatedMedium` con un campo `private` proprio ciascuna (mai letto) — non sottoclassi vuote, altrimenti TypeScript le tratterebbe come strutturalmente intercambiabili (bug trovato dalla revisione, vedi voce #51). **Voce #56**: `SimulatedMedium` guadagna un secondo registro indipendente da quello dei device connettibili — `registerBroadcastListener()`/`unregisterBroadcastListener()`/`broadcast(fromDeviceId, packet)`, quest'ultimo consegna a ogni listener (tranne il mittente) una copia indipendentemente `decodePacket(encodePacket(...))`-round-tripped, mai un riferimento condiviso mutabile. Ogni `SimulatedLinkTransport` si registra anche come broadcast listener in `start()`/si de-registra in `stop()` — così un qualunque Relay Mode con radio simulata sente i broadcast senza wiring aggiuntivo. `receiveBroadcast()` applica un rate limit **globale per-transport, non per mittente** (`MAX_BROADCAST_PACKETS_PER_WINDOW`/`BROADCAST_WINDOW_MS`) prima di inoltrare a `packetHandlers` con `fromPeerId = packet.source` — deliberatamente non per-identità, un'identità usa-e-getta la aggirerebbe banalmente (stesso ragionamento di `InternetGateway`, voce #45). Questo limite da solo **non** basta a impedire la crescita illimitata di `RateLimiter.windows` (vedi `rate-limit.ts` sotto per il fix reale, trovato da code-review).
- `transports/beacon-broadcast.ts` (voce #56) — `BeaconBroadcastTransport`, **non implementa `Transport`** (nessun `connect()`/`onPeerConnected()` avrebbe senso per un dispositivo che non accetta mai connessioni in ingresso). API minima: `constructor(deviceId, medium)` + `advertise(packet: Packet): void` → `medium.broadcast(deviceId, packet)`. Generico su `BleMedium`/`LoraMedium` (nessuna duplicazione radio-specifica). Wired in `node.ts` via `NomadNode.setBroadcastTransport()`, deliberatamente separato da `addTransport()` — non deve mai entrare in `this.peers`/`floodExcept()`.
- `transports/lora.ts` (voce #51) — `LoraSimulatedTransport`/`LoraMedium`, una `SimulatedLinkTransport` configurata con i numeri LoRa: MTU 200 byte (payload fisico reale di un pacchetto LoRa grezzo, non rimpicciolita come BLE), latenza 250ms per frammento (due ordini di grandezza sopra i 5ms di BLE — questo, non l'MTU, è il parametro che differenzia le due radio, per scelta esplicita dell'utente), 16 connessioni massime (contro 7 di BLE — nessun vincolo fisico "GATT" per LoRa). Duty-cycle del canale condiviso (EU 868MHz, ~1% legale per sotto-banda) non modellato in questa versione, limite noto e dichiarato.
- `routing.ts` — `SeenCache` (dedup) + `decideForward()`, il cuore del controlled flooding (spec §21).
- `routing-table.ts` — routing a costo distance-vector (spec §22), alternativa/complemento al flooding per traffico unicast.
- `content.ts` — `ContentStore` (limitata per dimensione, `BoundedFifoMap`, voce #32 — eviction pesata sulla fiducia, con un rank dedicato per il contenuto pubblicato localmente), firma/verifica dei contenuti, `ChunkAssembler`, scadenza (`expiresAt`).
- `catalog.ts` — `RemoteCatalog`, contenuto noto ma non ancora scaricato (sync tra segmenti di rete).
- `service.ts` / `service-directory.ts` — service discovery (spec §35-37), stesso schema di firma di `content.ts`.
- `store-and-forward.ts` — `PendingDeliveryQueue`, coda per pacchetti unicast non consegnabili subito. Eviction pesata su priorità (voce #55, `docs/beacon.md` "NOMAD Mobile Relay" — un corriere a memoria vincolata non deve mai sacrificare una voce `Priority.EMERGENCY` per fare spazio a traffico ordinario) e TTL differenziato (`ttlMs`/`emergencyTtlMs`, quest'ultimo più lungo). `priorityRank()` applica lo stesso clamp difensivo di `priority-queue.ts` su `packet.priority` (mai validato da `decodePacket()`) prima di usarlo nello score di eviction — altrimenti una priorità forgiata/fuori range potrebbe rendersi immune all'eviction. `requeue()` (usato da `NomadNode.flushPendingDeliveries()` sul percorso di ri-accodamento dopo un rigetto del gate di relay) porta avanti l'`expiresAt` originale di una voce invece di calcolarne uno nuovo — altrimenti una voce ripetutamente ri-accodata (il caso normale per un corriere che si riconnette spesso) non scadrebbe mai.
- `trust.ts` — `TrustLevel`/`TrustManager` (spec §54).
- `rate-limit.ts` — budget di pacchetti per peer per finestra temporale (`RateLimiter.windows`, ora `BoundedFifoMap`, `maxTrackedPeers` default 4096 — voce #56, trovato da code-review: un pacchetto ricevuto via broadcast (`transports/simulated-link.ts`'s `receiveBroadcast()`) non ha mai un evento di disconnessione che chiami `reset()`, e `packet.source` non è autenticato — un mittente che genera un'identità usa-e-getta per pacchetto (il caso "Card usa-e-getta" che il Beacon esiste per supportare) faceva crescere questa mappa senza limite; il rate limit globale del transport da solo rallenta ma non impedisce la crescita, ogni pacchetto entro quel budget raggiunge comunque `allow()` con un `fromPeerId` distinto).
- `relay-policy.ts` — quando un nodo fa da relay in base a batteria/carica auto-dichiarata.
- `encryption.ts` — E2E per messaggi privati (X25519 + AES-256-GCM), `IdentityAnnouncement`.
- `peer-directory.ts` — propagazione delle chiavi di cifratura tra peer.
- `message-history.ts` — `MessageHistory` (voce #36), cronologia locale (mai firmata/propagata) dei messaggi 1:1 inviati/ricevuti via `sendPrivateMessage()`/`handlePrivateMessage()`, bounded su conversazioni (`maxPeers`, eviction pesata sulla fiducia) e messaggi-per-conversazione (`maxMessagesPerPeer`). Esporta anche `MAX_MESSAGE_TEXT_LENGTH`, il limite canonico di lunghezza di un singolo messaggio — importato sia da `node.ts` (`extractChatText()`, applicato sia in invio che in ricezione, solo per i messaggi 1:1) sia da `web-ui.ts` (`POST /api/messages`) sia da `public-channels.ts` (`extractChannelMessagePayload()`), un solo posto per non farli divergere.
- `public-channels.ts` — `PublicChannels` (voce #40), vista locale (mai firmata indipendentemente — vive sopra `content://` già firmato) dei canali pubblici di chat non cifrati, popolata da `NomadNode.publishChannelMessage()`/`considerChannelMessage()` (node.ts). Convenzione sul nome `chat:<canale>` per `ContentMetadata.name` (`channelContentName()`/`parseChannelFromContentName()`, quest'ultima difensiva contro un `name` non-stringa — `verifyContentSignature()` prova solo che la firma corrisponda, mai la forma). Il payload firmato è `{ text, timestamp }` (`extractChannelMessagePayload()`) — il timestamp vive nel payload, non in `ContentMetadata.createdAt`, che non è coperto dalla firma del publisher. Bounded su canali (`maxChannels`, eviction pesata sul **massimo** tra le fiducie di tutti gli autori visti nel canale, non solo l'ultimo — `bestAuthorTrust()`) e messaggi-per-canale (`maxMessagesPerChannel`).
- `drops.ts` — `Drops` (voce #47, bacheca "drop" — concetto ispirato al `BoardManager` di BitChat, Unlicense/dominio pubblico, mai `LocationNotesManager`, vedi `docs/reuse-vs-new.md`), mirror di `public-channels.ts` ma su un solo asse bounded (`maxDrops`, non c'è raggruppamento per canale) — nome fisso `DROP_CONTENT_NAME = "drop"` (non un prefisso: l'identificatore è già il `contentId`). `extractDropPayload()` valida `{ text, lat, lon, label?, urgent, timestamp }` con gli stessi bound di `extractChannelMessagePayload()`/`extractLocationReport()`. Popolata da `NomadNode.publishDrop()`/`considerDrop()` (node.ts). Scadenza pigra in `list()`, come ogni altra struttura di questa famiglia.
- `bounded-map.ts` — `BoundedFifoMap<K,V>`, struttura dati limitata condivisa (con eviction opzionale pesata su uno score, es. la fiducia) usata da quasi tutte le strutture sopra che vengono alimentate dalla rete. Esporta anche `pushBounded()` (voce #40), l'helper "push poi trim" condiviso da `MessageHistory.record()`/`PublicChannels.record()`/`Groups.recordMessage()` — guardia esplicita su `maxLength <= 0` per evitare un loop infinito con un valore negativo.
- `groups.ts` — `Groups` (voce #42), chat private/di gruppo cifrate end-to-end (membership fissa alla creazione, v1 — nessuna uscita/rimozione membro né rotazione di chiave, scelta esplicita dell'utente). `GroupInfo` (chiave AES-256-GCM del gruppo solo in memoria, mai persistita), `extractGroupInvite()` (valida un payload `PRIVATE_MESSAGE` discriminato `type: "group-invite"`), `groupMessageSigningPayload()`/`signGroupMessage()`/`verifyGroupMessage()`/`decryptGroupMessage()` (cifra+firma un `GROUP_MESSAGE`: AES-256-GCM con la chiave di gruppo via `encryptForPeer()`/`decryptFromPeer()` già esistenti, più una firma Ed25519 del mittente via `Identity.sign()`/`Identity.verifyWithNodeId()` — necessaria perché con una chiave condivisa l'auth tag GCM da solo non impedisce a un membro di impersonarne un altro). `GroupMessage.messageId` = la firma del mittente (deterministica per EdDSA), usato da `Groups.recordMessage()` per scartare un replay dello stesso payload firmato reinviato con un `packet.id` diverso — `SeenCache` deduplica solo per `packet.id`, mai per contenuto. `Groups` tiene info+cronologia di ogni gruppo in un'unica `BoundedFifoMap` (mai due mappe separate, per non rischiare stato orfano tra eviction indipendenti), bounded su gruppi (`maxGroups`, eviction pesata sulla fiducia di chi ha invitato) e messaggi-per-gruppo (`maxMessagesPerGroup`).
- `location-registry.ts` — `LocationRegistry` (voce #44), stato locale mesh-interno (come `groups.ts`/`public-channels.ts`, non un adapter esterno) di posizioni condivise opportunisticamente. `extractLocationReport()` valida un payload `PRIVATE_MESSAGE` discriminato `type: "location-report"` (lat/lon/accuracy?/timestamp, stesso pattern di `extractGroupInvite()`). `LocationRegistry.record()` **sovrascrive sempre** l'entry esistente per lo stesso `reporterId` (mai accumula, "solo l'ultima posizione nota") **a meno che** il nuovo report non abbia un timestamp strettamente più recente di quello già in archivio — guardia anti-fuori-ordine per store-and-forward (un report vecchio in coda non deve mai regredire uno più recente già arrivato per una via più veloce), con `report.timestamp` clampato a `Math.min(report.timestamp, Date.now())` per impedire che un timestamp futuro fabbricato avveleni permanentemente uno slot (entrambe le guardie trovate da code-review, vedi voce #44 per il dettaglio, incluso il limite accettato e documentato sul clock rollback locale). ## Convenzioni consolidate (da rispettare per coerenza, non da riscoprire)

- **Ogni struttura dati alimentata dalla rete è limitata per dimensione** (spec §57): usa `BoundedFifoMap` con `maxSize`, e quando la fiducia dell'origine è nota passa `evictionScore`/`trustRank` così l'eviction preferisce rimuovere la voce meno fidata invece della più vecchia — altrimenti un peer può fabbricare identità usa-e-getta per sfrattare voci legittime (vedi bug #13 in `security.md`). Strutture puramente locali (mai alimentate da pacchetti di rete, es. `localServices` in `node.ts`) non hanno bisogno di questo limite.
- **Ogni claim che arriva dalla rete e verrà ri-propagato ad altri peer viene firmato dal suo autore** (Ed25519, stesso pattern in `content.ts`/`encryption.ts`/`service.ts`): un campo `SignableXFields`, una funzione `xSigningPayload()` con ordine esplicito dei campi, una `verifyX()` che riverifica contro la chiave pubblica dichiarata. Un relay non fidato può inoltrare ma mai fabbricare un claim valido per un'identità che non controlla.
- **Il payload di un pacchetto non è mai fidato quanto il suo tipo dichiarato**: `decodePacket()` valida solo l'involucro (id/type/source/ttl), mai la forma del payload — ogni handler deve accedere ai campi del payload in modo difensivo (`packet.payload?.campo`, controlli `typeof`/`Array.isArray`), perché un singolo pacchetto malformato da un peer connesso non deve mai poter far crashare il processo. Questo ha causato almeno un vero DoS non autenticato scoperto dalla revisione (voce #6, bug #16) — vedi `tests/integration/malformed-packet-robustness.test.ts` per il pattern di test dedicato, da estendere per ogni nuovo tipo di pacchetto.
- **Scadenza "pigra", mai un timer di sweep in background**: `ContentStore`/`RemoteCatalog`/`ServiceDirectory` trattano una voce scaduta come assente ed eliminano al momento dell'accesso (`get`/`has`/`list`/`size`), non con un `setInterval`.
- **`packet.source` non è mai autenticato crittograficamente** (limite noto e documentato in `security.md` sotto "Binding crittografico") — chiunque può dichiararsi qualunque node id nel campo `source`. Ciò che *non* può fare è produrre una firma valida per un'identità che non controlla. Ogni nuovo meccanismo che si affida a `packet.source` per decidere qualcosa di sensibile (es. quale risposta accettare per una richiesta pendente) deve comunque vincolarsi al mittente atteso (es. `packet.source === entry.activeProvider`), non fidarsi ciecamente — pattern già usato in `handleContentChunk`/`handleContentComplete`/`handleServiceResponse`.
- **Nessuna nuova dipendenza esterna senza necessità reale**: `web-ui.ts` usa `node:http` puro invece di aggiungere Express; `tcp.ts` non usa framework di parsing. Il solo devDependency oltre a TypeScript/vitest/tsx è quanto già presente.
- **Test**: unit in `tests/unit/` (logica pura, nessuna rete reale), integration in `tests/integration/` (istanze reali di `NomadNode`/`TcpTransport` su localhost, a volte con socket grezzi via `node:net` per controllo deterministico del timing quando serve simulare un comportamento avversariale/di rete inaffidabile — vedi `content-provider-retry.test.ts` per il pattern). Non usare mock per `NomadNode` stesso: la suite esistente preferisce nodi reali connessi via TCP reale su porta `0` (assegnata dal SO), anche nei test più intricati.
- **Race di timing nota e ricorrente nei test**: `connect()` che si risolve garantisce solo che il lato che ha iniziato la connessione abbia identificato il peer, non che l'altro lato abbia già processato l'HELLO in arrivo. Se un test fa qualcosa sul lato "server" subito dopo che `connect()` si risolve sul lato "client" (es. registrare un servizio e aspettarsi che venga floodato al peer appena connesso), potrebbe fallire in modo intermittente — aggiungere un `waitFor()` esplicito sullo stato effettivamente osservabile (es. `provider.node.peers.has(caller.node.nodeId)`) prima di procedere.

## Comandi utili

```bash
npm install                                    # alla radice, installa anche il workspace node/
npx vitest run                                 # intera suite di test
npx vitest run tests/integration/xyz.test.ts   # un file specifico
npx tsc --noEmit -p node/tsconfig.json         # typecheck senza emettere output
npm run build -w node                          # build del package node/
npm run dev -w node -- --id A --port 9001      # avvia un nodo (aggiungi --web-port 8080 per l'UI web)
npm run simulate -- --nodes 50 --topology random  # simulatore di rete a scala
npm run hub -- --port 8420                     # avvia la NOMAD Hub Management API (aggiungi --fake-docker senza Docker reale)
```

## Cosa NON fare

- Non commitare/pushare senza che i test passino ripetutamente, il typecheck e la build siano puliti.
- Non saltare il passaggio di code-review su una voce "perché sembra semplice".
- Non procedere alla voce successiva senza l'ok esplicito dell'utente, anche se la precedente sembra ovviamente completa.
- Non introdurre dipendenze esterne per problemi risolvibili con la libreria standard di Node.
- Non fidarsi di `packet.source` o della forma del `payload` di un pacchetto in arrivo senza validazione difensiva.
